## 01 · 一次 run

审稿总结（不念）：内核是同一个 Agent 循环；一次 run 四步；会话可跨 run；睡的是模型；引出简报例子。

- 它干活的方式，和你平时用的 Agent 一样：模型调工具、看结果、再调工具，直到做完。多出来的是外面一圈：什么时候叫醒它，两次之间记住什么，做完怎么告诉你。
- 看这张图。灰色是睡着；中间那一小格是醒着干活的一段，文章管它叫一次 run。
- 每次醒来就四步：收到一件事；打开这件事的记录，文章叫会话；干活；最后把要记住的东西存下来。
- 睡着的时候不调用模型，所以一个 token 都不花，外面只留几个很轻的程序，负责接事件、看时间。
- 这类 Agent 最近多起来，Anthropic 说是因为模型更会判断什么时候该来问一句，也更便宜了，长任务上降得最多。
- 下面拿一个例子贯穿：一个 Agent，每天早上给你发一份简报。文章提过这个例子，后面的流程是我们按文章的规则推的。

> 屏幕卡：Run 四步 An event arrives → A session starts → The agent loop runs → The run writes back｜A run works inside a session, which is the transcript of messages and tool calls

## 02 · 事件收件箱

审稿总结（不念）：直接调用会抢跑、会丢；先落表，一个 worker 取。

- 它睡着的时候，谁来叫醒它？靠事件：你发来的消息；webhook，也就是别的系统有变化时主动推过来的通知；还有定时任务和后台作业。
- 一个很自然的做法，是让每个事件源直接调用 Agent。文章说这样会出问题，比如两个事件同时到，会同时起两次 run，互相抢；一崩溃，事件可能整个丢掉。
- 所以中间加一个收件箱，事件源只往里写。它有三件东西：一张数据库表存事件；一个 handler，通常是个 HTTP 接口，往表里写；一个 worker，后台服务，从表里读。
- 新事件进来，handler 写表，叫醒 worker；worker 读出待处理的事件，起一次 run，跑完标成已完成。表里记着状态，重复的事件按 ID 去掉。
- 文章还给了几条经验。handler 要马上回应，深一点的检查放到 run 里做。worker 醒来自己去表里拉事件，中途死了，换一个还能重试。
- 文章建议先给每个用户一个收件箱，同一时间只让一个 worker 处理，免得两次 run 重复干活、互相覆盖。你连发三条消息，worker 合成一次 run，Agent 只回你一次。
- 用户的回复这类接着上次的事，续上原来的会话；别的事件开新会话。

> 屏幕卡（原文图）：Handler（HTTP endpoint）→ Event inbox（database table, tracks status, drops duplicates）→ Worker（reads pending, starts run, marks done）
> 屏幕卡：原文 has a few failure modes. For example…｜acknowledge events quickly（e.g. prompt injection checks during the run）｜the inbox should be the source of truth｜only one active worker at a time｜batch pending events together｜one inbox per user

## 03 · 定时器

审稿总结（不念）：闹钟有两种；到点了也是一个事件，走同一个收件箱。

- 光有收件箱，它还是在等别人来叫。要主动，得有闹钟，这就是定时器。
- 它分两种。follow-up 是 Agent 给自己定的，比如过两天看看对方回没回；schedule 是按固定节奏重复的任务，通常由用户来定，每日简报就是一个 schedule。
- 定时器存在自己的表里，和收件箱分开，因为收件箱只放现在就能处理的事件。
- 定时器自己不会启动 run。有一个 scheduler，也是后台服务，隔一段时间扫一遍这张表：到点的 follow-up 标成完成，schedule 把时间改到下一次，然后往收件箱写一个事件，叫醒 worker。
- 简报定在早上九点，九点一过，scheduler 把下次改成明天九点，再往收件箱写一个事件。
- 到点了也只是变成一个事件，走同一个收件箱，单个 worker、重试、去重这些好处都用得上。

> 屏幕卡（原文图）：A run sets a timer → Timers（follow-up set by the agent / schedule set by the user，原图示例 Fri 09:00 Daily newsletter）→ Scheduler finds what's due → Event inbox
> 屏幕卡：原文 A timer doesn't initiate a run on its own｜durable execution engine

## 04 · 记忆

审稿总结（不念）：只存查不回来的东西；四类，每次只加载小的那几个；dreaming 可选。

- 每次 run 都是断开的，连续性靠记忆。文章的做法是一个文件目录，落在数据库或者对象存储里，worker 没了，记忆还在。
- 经验法则是：**记忆只存查不回来的东西**。已经在别的系统里的，比如工单系统里的任务，存一个指针就够了。
- 文章建议存四类，文件名用的是它示例图里的叫法。
- instructions.md，存用户对 Agent 的要求，每次 run 都加载。简报里，就是你说过的「只要 Agent 相关的新闻」。
- notes 文件夹，存它学到的关于用户的事，比如偏好、被纠正过的地方。
- reported.md，存已经告诉过用户什么，每次都加载，昨天发过的，今天就不再发。
- progress 文件夹，每个进行中的任务一个进度文件，下一次 run 读它接着干。
- notes 和 progress 这两个文件夹，平时只加载一个索引，要细节再去读。所以每次 run 开头只装几个小文件，上下文保持精简。
- 这些都是在 run 里写的。文章说还可以加一个 dreaming：在 run 之外单独跑一个整理任务，回头看过去的会话，替换过时的记忆。Anthropic 11 月 6 号那篇记忆文章专门讲过它，我们也拆过。

> 屏幕卡（原文示例图 one example setup）：instructions.md Every run｜index.md Every run｜reported.md Every run｜notes/ When needed｜progress/ When needed
> 屏幕卡：原文 memory should only hold what the agent can't look up again｜save a pointer instead｜Claude Code auto memory、memory tool 都是 a directory of files
> 屏幕卡：dreaming：原文 You can also add dreaming｜our post on agent memory → 《The components of agent memory》，2026-11-06（本片对号）
> 屏幕卡：原文 keeping it lean and using prompt caching｜compact or start a new session — both lose detail

## 05 · 权限

审稿总结（不念）：风险最大；凭证不进 Agent；分类器拦危险操作；要人批的先停下，回答作为事件续上。

- 文章说，权限是风险最大的地方：一次 run 拿着用户的访问权限，而且就是设计成没人看着跑的。
- 每次调用工具，都要定下来：直接执行，拦下来，还是等用户批准。文章说，管这件事的还是普通 Agent 也有的三样：凭证、auto mode、延后的工具调用。
- 一是凭证。在 Agent 的环境外面放一个代理：Agent 发出的请求不带密码和 token，代理转发前把真凭证加上去。简报要登录的网站，就走这个代理。
- 二是 auto mode，Claude Code 里已经有一版：用分类器，专门判断高风险操作危不危险，危险的就拦下，让 Agent 换个更安全的做法。文章也说，最重要的决定还得用户审一遍。
- 三是延后的工具调用。要用户批准或者补充信息的操作，这次调用先不执行，run 结束，会话停在这次调用中间存下来。
- 请求推给用户，比如一张能直接点的卡片。用户的回答作为新事件进收件箱，起一次新 run，接着刚才存下的会话往下走。这段时间 worker 照样处理别的事件。

> 屏幕卡：原文 Permissions are where always-on agents carry the most risk｜proceed on its own, block it, or wait for approval｜the same ones other agents use
> 屏幕卡：Credential store：proxy outside the agent's environment injects credentials｜Auto mode：classifiers review higher-risk actions｜User review is still necessary for the most important decisions｜Deferred tool calls：session saved mid-call（e.g. interactive card built with MCP Apps）

## 06 · 发件箱

审稿总结（不念）：三种结束方式；正式发件箱只在要控节奏、要能恢复时才需要；发多少靠评测。

- 第五样是发件箱，管结果怎么送到你手上。普通 Agent 边生成边推给你；always-on agent 的活大多在后台干完，你只拿到结果和少量细节。
- 一次 run 有三种结束方式：发一条消息；判断这次没什么要说的；或者用刚才那种延后调用来问用户。
- 多数情况下，一个 send 工具直接发给用户就够了。要控制发消息的节奏，或者出错了要能恢复，才需要正式的发件箱：一张待发消息的表，加一个叫 dispatcher 的后台服务，决定发哪些、什么时候发。
- 另一件要调的是发多少。发太多是噪音，发太少会漏掉要紧的事。Anthropic 建议做评测来找平衡，一开始宁可少发。

> 屏幕卡（原文图）：A run ends with：nothing to say / a send tool call / a deferred tool call｜Outbox（database table）→ Dispatcher → The user
> 屏幕卡：原文 recover from errors｜We recommend building evals to find the right balance｜start quiet and then earn more of the user's attention over time

## 07 · 合起来

审稿总结（不念）：用每日简报把总图完整走一遍。

- 把五样连起来，走一遍简报。
- 九点，scheduler 往收件箱写一个事件。worker 取到它，开一个新会话，起一次 run。
- Agent 先读 instructions.md，知道你只要 Agent 相关的新闻；再读 reported.md，昨天发过的跳过。
- 要登录的网站由代理加凭证；写好简报，发出去，再把这次发了什么记进 reported.md，然后睡回去。
- 你回了一句：第二条多讲点。这条回复作为事件进收件箱，续上刚才那个会话，再跑一次。
- 每次 run 都很短，醒了又睡一直在重复，所以用户觉得它一直在线。

## 09 · 结尾

审稿总结（不念）：总结卡；讨论问题；固定结尾。

- 收件箱：事件先落表，同一时间只让一个 worker 处理。
- 定时器：到点了也只是往收件箱写一个事件。
- 记忆：只存查不回来的东西，每次加载的部分要小。
- 权限：凭证放在 Agent 外面，要人批的地方先停下来。
- 发件箱：发多少靠评测，一开始宁可少发。
